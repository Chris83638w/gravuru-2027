# QR-Seiten: Erinnerungsseite (Andenken) und Geschenkseite (Geschenkideen)

Stand: 10.11.2026 · Operator: Claude · Umsetzung: Astra 1 · Branch `dev/qr-seiten-20261110` · Übergabe: [2026-11-10-qr-seiten-astra1.md](../handoffs/2026-11-10-qr-seiten-astra1.md)

## 1. Auftrag (Quelle: Chris, Chat 10.11.2026)

Eine Gedenktafel (und andere Produkte) trägt einen QR-Code. Wer ihn scannt, sieht eine Online-Seite mit Fotos und Text. Das gibt es zweimal: für **Andenken** und für **Geschenkideen**. Claude ist Operator und Boss, Astra 1 baut.

Gemeint sind zwei Seitentypen, die zu den zwei Produktbereichen im Shop passen:

| Typ | Produktbereich | Zweck |
| --- | --- | --- |
| `erinnerung` | Andenken (Gedenktafeln, Grabstecker, Gedenkherzen …) | Ruhige Gedenkseite für einen Menschen oder ein Tier |
| `geschenk` | Geschenkideen (Fotogeschenke, Schlüsselanhänger, Brettchen …) | Persönliche Botschaft zum Geschenk, vom Beschenkten per QR-Code aufrufbar |

## 2. Grundentscheidung des Operators: Code und Inhalt sind getrennt

Der QR-Code enthält **nur eine kurze, zufällige Kennung** (`<BASE_URL>/s/<code>`), keine Namen, keine Daten. Der Inhalt der Seite wird vom Kunden **nach dem Kauf** gepflegt.

Warum so:
- Die Produktion (Gravur/UV) wird nie durch fehlenden Seiteninhalt blockiert.
- Der QR ist für immer auf dem Produkt. Die Seite dahinter darf sich ändern, der Code nicht.
- Kurze Kennung = weniger QR-Module = besser lesbar auf kleiner Fläche (Details unter 7).

Das ist ein Vorschlag des Operators und keine Entscheidung von Chris. Ändert Chris es, ändert sich nur Abschnitt 4.

## 4. Ablauf

1. **Code vergeben.** Ein interner Aufruf (Server-zu-Server, Schlüssel aus Umgebungsvariable) legt pro Bestellposition einen Code an: Typ, Code (10 Zeichen, Crockford-Base32 ohne verwechselbare Zeichen), geheimes Bearbeiten-Token. Die Bestellung speichert nur den Code.
2. **QR erzeugen.** Reine Funktion `qrSvg(url)` liefert ein Vektor-SVG in Modulen (ohne feste Größe), damit die Werkstatt-Pipeline es später 1:1 in mm setzen kann.
3. **Kunde bearbeitet.** Er bekommt einen Bearbeiten-Link `<BASE_URL>/bearbeiten/<token>` (Zustellung per Bestell-Mail ist ein späterer Anschluss, nicht dieser Auftrag). Er füllt die Seite, sieht die Vorschau, veröffentlicht.
4. **Besucher scannen.** `/s/<code>` zeigt die Seite. Unveröffentlicht oder gesperrt: freundliche Platzhalterseite ohne Inhalt.

## 5. Seiteninhalte (Startumfang)

**Erinnerungsseite:** Name · Lebensdaten als Freitext (Mensch oder Tier, keine Datumsprüfung) · Hauptfoto · weitere Fotos · Text (Abschiedsworte oder Gedicht).

**Geschenkseite:** Titel · Widmung (für wen, von wem, Freitext) · Botschaft · Fotos.

Bewusst **nicht** im Startumfang, weil Chris sie nicht genannt hat: virtuelle Kerze, Video (auch als Link), Gästebuch, Musik. Wer eine davon will, sagt es; dann kommt sie als eigenes Paket.

Beide Typen:
- Mobil zuerst, ohne Tracking, ohne Fremdschriften, ohne Cookies.
- `noindex`: Seiten erscheinen nicht in Suchmaschinen.
- Footer mit Impressum und Datenschutz (Links auf die Shop-Seiten, Adressen per Konfiguration).
- Kunden können die Seite jederzeit auf „nicht veröffentlicht“ stellen.

## 6. Technik (Entscheidungen des Operators)

- Eigener Ordner `app/seiten-dienst/`, Node ESM wie der Rest (`engines` ≥ 24), eigener Port, **keine Änderung** an `app/configurator/` oder `app/workshop/`.
- Datenbank: eingebautes `node:sqlite` (keine neue Abhängigkeit). Hat der Zielhost kein passendes Node, **melden**, nicht still eine Datenbank-Abhängigkeit hinzufügen.
- Daten- und Uploadordner per Umgebungsvariable **außerhalb** des Repos. Uploads: nur JPEG, PNG und WebP, Prüfung am Dateikopf (nicht an der Endung), Metadaten (EXIF/GPS) beim Speichern entfernen, Bilder verkleinert ausliefern.
- QR-Erzeugung: eine einzige abhängigkeitsfreie, MIT-lizenzierte Bibliothek mit fester Version; Wahl und Begründung in der Übergabe festhalten. Kein Netzwerkzugriff beim Erzeugen.
- Sicherheit: Bearbeiten-Token zufällig (mind. 128 Bit), in der Datenbank nur als Hash; Anfragenbegrenzung auf Bearbeiten und Upload; HTML-Ausgabe strikt maskiert; Content-Security-Policy ohne Fremdquellen; Uploads nie als ausführbar ausliefern.
- Betrieb: Sperrfeld `status` (`entwurf`, `veroeffentlicht`, `gesperrt`), Admin-Schnittstelle zum Sperren, Exportieren und Löschen einer Seite samt Dateien (Löschpflicht auf Kundenwunsch), Sicherungsskript für Datenbank und Uploads. **Nichts löschen ohne Ankündigung** gilt auch für das Löschen im Dienst: Löschen nur auf ausdrückliche Anforderung, mit Protokolleintrag.

Lesbarkeit hängt von Material, Verfahren (Gravur oder UV-Druck), Kontrast und Größe ab. Diese Werte werden **nicht geschätzt**.
