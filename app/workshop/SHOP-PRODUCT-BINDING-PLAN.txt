Schnittstelle

planShopProductBindings({tenantId,shopDomain,shopifyEvidence,selections,adapter,
                        now,maxEvidenceAgeMs})

shopifyEvidence = {
  tenantId, shopDomain, readAt: ISO-Zeit des tatsächlichen Admin-Abgleichs,
  complete:true,
  products:[{id:ProductGID,
             variants:[{id:VariantGID,productId:ProductGID,priceCents}]}]
}
complete bedeutet vollständige Variantenlisten für alle Produkte dieses Belegs,
nicht zwingend den gesamten Shop. Der Aufrufer muss Pagination/Fehler zuvor prüfen.
Der Plan selbst macht keine Netzabfragen und kann die Herkunft eines Belegs nicht
kryptografisch beweisen. Nur vom Server erzeugte, vertraute Belege verwenden.
maxEvidenceAgeMs ist eine explizite Betreiber-/Aufruferentscheidung; kein stiller
Standard. Abgelaufene oder zukünftige Belege werden verworfen.

selections = [{shopifyProductId:ProductGID,shopifyVariantId:VariantGID,
               productId:cfg_ID,productRevision:INTEGER,options:{...}}]
Ein expliziter Zielstand je Shopify-Variante. Keine SKU-Suche im Kundenpfad.
SKU darf beim einmaligen Import helfen, muss dort eindeutig auf IDs aufgelöst sein.

adapter = {
  tenantId, shopDomain, storeId,
  getCurrentProduct(id),
  resolveSelection(record,options),
  resolveProductionProfile(document),
  getBindings()
}

storeId ist eine vom Server festgelegte interne Kennung des privaten Datenspeichers,
kein Pfad und keine Kundeneingabe. Zwei Datenbanken desselben Shops/Tenants bleiben
so unterscheidbar. Beim Auflösen muss die storeId weiterhin übereinstimmen.
Alle Adapter sind synchrone, private Lesezugriffe. Der spätere Host muss sicherstellen,
dass Repository, OrderIntake und Profilspeicher demselben Tenant und Shop gehören.
Bei der späteren Verdrahtung:
- getCurrentProduct -> repository.get(id), ohne historische Revision auszuwählen.
- getBindings -> orderIntake.bindings().filter(b=>b.shopDomain===shopDomain),
  aktueller tenantgebundener Store. Die vorhandene API listet tenantweit alle Shops.
- resolveProductionProfile -> productionProfiles.resolve(document).
- resolveSelection -> exakt eine Variantenzeile aus prepareShopProduct(record).variants
  anhand kanonischer options wählen; Rückgabe {options:variant.options,
  unitCents:variant.priceCents}. Das nutzt bestehende Varianten-/Preislogik für
  native und form; keine Kontur-/Designkonvertierung. Vollständige resolvedOptions
  dürfen Kunden-Zusatzfelder enthalten und sind deshalb hier NICHT die Quelle.
  Der Plan sperrt native Auswahlkeys außerhalb der echten optionGroups zusätzlich.

Die Auflöser prüfen Verfahren/Material/Stärke weiterhin nach ihren bestehenden Regeln.
Der Plan setzt ein tatsächlich zugeordnetes, auflösbares Fertigungsprofil voraus und
liefert dessen ID, Revision und SHA. Fehlt es, entsteht ein expliziter Planungsfehler.
Das ist keine Fertigungsfreigabe; Profilblocker, ICC und reale Maschinenprobe bleiben offen.

resolveShopProductBinding(plan,{tenantId,shopDomain,shopifyProductId,shopifyVariantId,
                               adapter,now})

Die Auflösung erfordert exakt beide Shopify-GIDs und denselben Kontext. Sie prüft
Aktualität und Unverändertheit von Produktdokument, Optionen, Profilstand und Bindung
erneut. In einem neuen Prozess muss ein Plan aus aktuellen Belegen neu erstellt werden;
deserialisiertes JSON wird nicht als geprüfter Plan akzeptiert.

Ausgabe pro Zuordnung:
- Shopify-Produkt-/Varianten-GID; numerische variantId für die bestehende Binding-API.
- cfg-ID, feste Revision, Schema, Dokument-SHA, normalisierte Optionen, Basispreis.
- productionProfileRef:{id,revision,sha256}.
- binding:{mode:'reuse',id:existingBindingId} oder {mode:'bind-required',id:null}.
- immer mode:'plan-only', publicAccess:false, checkoutEnabled:false.

Vorhandene historische Bindungen bleiben unberührt und werden nicht automatisch
auf die neueste Produktrevision umgebogen. 'bind-required' führt keinerlei bind()-Aufruf
aus. Ein späterer separater Aktivierungsschritt muss die bestehenden bind()-Validierungen,
Preisverträge und CAS-/Freigaberegeln weiterverwenden und dann einen frischen Plan bilden.
Der Plan ist weder Kunden-Authentifizierung noch dauerhaftes Aktivierungsregister.
